# Обновление портала на сервере

Короткая инструкция для того, кто разворачивает сборку на riv.kz.

## 1. Обновить код и собрать

```bash
git pull
npm ci
npm run build
```

`npm run build` сам накатывает миграции БД (`prisma migrate deploy`) и запускает
идемпотентный сид, поэтому отдельно их запускать не нужно. После сборки —
перезапустить приложение (в IIS: перезапуск сайта / пула приложений).

## 2. ⚠ Обязательно: AUTH_SECRET

**Без этой переменной новая сборка не пустит в систему никого — это защита, а не
поломка.** Раньше при отсутствии `AUTH_SECRET` код подписывал сессии строкой,
лежащей в открытом репозитории: зная её, любой мог подделать cookie
администратора и войти без пароля.

Сгенерировать ключ:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Записать в `.env` рядом с приложением:

```
AUTH_SECRET=<сгенерированная строка>
```

Смена ключа разлогинивает всех, кто был залогинен, — один раз, это нормально.

Проверено на production-сборке: ключ читается **в момент работы**, а не
вшивается при сборке, и одинаково виден и обычным API-роутам, и middleware.
То есть достаточно положить его в `.env` и перезапустить приложение —
пересобирать из-за смены ключа не нужно.

Полный список переменных окружения: `DATABASE_URL`, `AUTH_SECRET`,
`ONEC_API_URL`, `ONEC_API_USER`, `ONEC_API_PASSWORD`, `ONEC_ORDERS_URL`,
`SYNC_ENABLED`, `SYNC_CRON`, `SYNC_SECRET`, плюс почтовые (см. ниже).

## 2.2 Почта: письмо менеджеру о новом заказе

Когда клиент оформляет заказ, менеджеру, к которому он привязан, уходит письмо
с составом заказа. Адрес берётся из карточки менеджера (поле Email), поэтому
он должен быть заполнен — иначе письмо уйдёт на запасной `ORDER_MAIL_TO`, а
если и его нет, отправка просто пропускается.

Переменные:

```
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_USER=<ящик компании>@gmail.com
SMTP_PASSWORD=<пароль приложения Google>
MAIL_FROM="Rival Auto" <<ящик компании>@gmail.com>
ORDER_MAIL_TO=<запасной адрес, необязательно>
SITE_NAME=www.rivalauto.kz
```

⚠ `SMTP_PASSWORD` — это **пароль приложения**, а не обычный пароль от почты.
Создаётся так: Google Аккаунт → Безопасность → включить двухэтапную
аутентификацию → «Пароли приложений» → создать, скопировать 16 символов.
Обычный пароль Gmail для SMTP не подойдёт.

Если почта не настроена, заказы оформляются как обычно — просто без письма:
сбой почты никогда не должен ломать продажу.

## 2.1 Сайт обязан открываться по HTTPS

В production cookie сессии выставляется с флагом `Secure`, поэтому браузер
отдаёт её обратно только по HTTPS. Если открыть портал по `http://` (или по
внутреннему IP без сертификата), получится обманчивая картина: логин
проходит успешно, но пользователя тут же выбрасывает обратно на страницу
входа, потому что cookie не возвращается на сервер.

На riv.kz HTTPS уже настроен — просто не тестируйте вход по `http://`.

## 3. Разовые задачи после первого обновления

Все скрипты по умолчанию **ничего не меняют** — сначала показывают, что
произойдёт. Для применения нужен флаг `--yes`.

```bash
# кто вообще есть в базе (паролей не печатает)
node scripts/list-users.mjs

# сменить пароль администратора (ввод скрытый, в базу уходит только bcrypt-хэш)
node scripts/set-password.mjs admin

# удалить старые демо-аккаунты manager/client/ra/accountant
node scripts/remove-demo-users.mjs          # проверка
node scripts/remove-demo-users.mjs --yes    # удаление

# перенести старые «личные скидки» клиентов в раздел «Скидки»
node scripts/migrate-personal-discounts.mjs         # проверка
node scripts/migrate-personal-discounts.mjs --yes   # перенос
```

**Про демо-аккаунты.** Прежняя сборка показывала на странице входа подсказку
`admin / admin123 · manager / manager123 · client / client123`. Эти аккаунты
могли остаться со стандартными паролями — тогда любой человек из интернета
видит цены, остатки и клиентскую базу. Проверить и удалить — в первую очередь.
Новый сид демо-пользователей больше не создаёт.

**Про личные скидки.** Раньше скидку можно было задать двумя способами: полем в
карточке клиента и правилом в разделе «Скидки». Поле убрано, но старые значения
в базе продолжают влиять на цену, оставаясь невидимыми. Скрипт переносит их в
раздел «Скидки» без изменения итоговой цены.

## 4. Особенность IIS: планировщик синхронизации

Синхронизация с 1С запускается внутри процесса приложения при старте
(`instrumentation.ts`). Если IIS поднимает несколько worker-процессов Node,
cron стартует в каждом из них — получится несколько параллельных синков,
одновременно дёргающих 1С.

Варианты: оставить один worker для сайта, либо выключить встроенный
планировщик (`SYNC_ENABLED=false`) и дёргать синхронизацию извне —
`POST /api/sync` с заголовком `X-Sync-Token: <SYNC_SECRET>` по расписанию
планировщика Windows.

## 5. Проверка после обновления

- страница входа открывается и на ней **нет** блока с демо-доступами;
- вход администратора работает (новым паролем);
- каталог показывает товары, дерево категорий — «Тормозные колодки», «Кузов»,
  «Фильтра» и т.д.;
- менеджер видит только своих клиентов, а в заказе разворачивается состав.
