### Интеграция с 1С (`lib/onec.ts`)

- Фид: `ONEC_API_URL` (Basic-auth), ~5400 товаров, синк ≈8–10 с.
- **Семантика синка (три правила, добытые разбором боевых багов):**
  1. **Первый импорт в пустой каталог НЕ ставит значок «Новинка»** — иначе вся витрина в значках (так и вышло при запуске).
  2. **Остатки, пропавшие из выгрузки, удаляются** (`stocksRemoved`): 1С перестаёт слать склад, когда товар кончился, и строка иначе висит вечно.
  3. **Товары, пропавшие из выгрузки, удаляются** (`productsRemoved`), **с защитой**: выгрузка меньше 50 % каталога → удаление пропускается, причина в `removalSkipped`.
- Заказы → 1С: `lib/onec-orders.ts`, POST `…/hs/v1/orders`. **Один документ на склад** (см. §3).
- Планировщик: `instrumentation.ts` → `lib/scheduler.ts` (cron из Setting `sync_cron`) + maintenance каждые 10 мин (`lib/maintenance.ts`).
- Скрытые категории: `Unused`, `Архив папки`. Фото: прокси `GET /api/image?u=` (SSRF-lock), диск-кэш `.image-cache/`.
- Кэш `lib/cache.ts` (in-process TTL): пользовательские ключи **обязательно** с `session.sub` (`wh:`, `disc:`), общие — `cfg:`, `catalog:`, `gifts:`.

### Дерево категорий (`lib/category-tree.ts`)

В 1С категории **плоские** (51 строка). Зонтики «Тормозные колодки», «Фильтра», «Ремкомплект» **в 1С не существуют** — структура задана явной картой в коде. Фильтр по группе разворачивается в точный список категорий (`categoriesUnderPath`), а не в поиск по префиксу. Категории вне карты падают в конец корня.

## 3. Knowledge Base — ключевые бизнес-правила

### Скидки и наценки (`lib/pricing.ts` — единственный источник истины)

- Берётся ЛУЧШАЯ скидка (max из `global_discount`, `User.discountPercent`, правил kind=DISCOUNT) и ЛУЧШАЯ наценка (max правил kind=MARKUP). **net = скидка − наценка**, cap ±95.
- **`isFinalPrice` блокирует ТОЛЬКО скидку. Наценка применяется ко ВСЕМ товарам, включая `isFinalPrice=true`.**
- **Клиент НЕ видит личную скидку.** В бейдж и зачёркивание идёт **ТОЛЬКО акция 1С** (из `oldPrice`, живёт `price_drop_days`). Нет снижения от 1С → нет бейджа вообще. Наценка тоже невидима — просто выше цена.
- Бейдж показывается, **только если итоговая цена реально ниже старой** — иначе наценка поверх акции рисовала зачёркнутую цену НИЖЕ текущей.
- Заказ пере-ценивается на сервере (`/api/orders`), клиентским ценам не доверяем; корзина при открытии делает репрайс.
- **Скидки живут только в разделе «Скидки»** (поле из карточки клиента убрано). Legacy-колонка `User.discountPercent` ещё учитывается → перенести `migrate-personal-discounts.mjs`.
- **Одно активное правило на скоуп:** API отклоняет второе правило с тем же клиентом/kind/target (и категорией/маркой) — 409 с id конфликтующего. Разные kind (скидка + наценка) сосуществуют; товарные правила не ограничиваются.
- **Менеджер видит и правит правила только своих клиентов** — включая PATCH/DELETE по id (раньше проверки владения там не было вовсе).
- **Персоналу скидка видна плашкой** в «Клиентах» и «Заказах» (`lib/discount-summary.ts`): зелёная −10 %, красная +5 %, «—», в подсказке разбор; адресные правила — отдельным счётчиком. Строки заказа с `isFinalPrice` помечены «без скидки».

### «Диски UIDNU» — строго парами (`lib/pair-only.ts`)

- Категория определяется точным сравнением `category` с «диски uidnu».
- В БД цена за 1 шт, но **карточка показывает цену ×2 с подписью «цена за 2шт»** (динамически: выбрал 4 → «цена за 4шт»).
- Количество строго чётное ≥ 2. `snapPairQty` продублирован на трёх уровнях: стор корзины, `/api/cart`, `/api/orders`.

### Подарки (`lib/gifts.ts` + `lib/gift-earn.ts`)

- Купи ≥ `minQty` товара-триггера → подарки бесплатно. **Кратность: floor(qty/minQty)**, правила стакаются. Количество триггера считается **суммарно по всем складам**.
- Сервер добавляет строки `price=0, isGift=true`; уходят в 1С, WhatsApp, почту, Telegram.
- В разбивке по складам подарок едет туда, где он в наличии, иначе — к складу первой платной строки (чтобы не уезжал в отдельный документ).
- **Подарки НЕ пересчитываются при правке заказа менеджером** — правило применилось при оформлении, оставлять ли подарок в урезанном заказе, решает менеджер вручную.
- **Тексты возврата в корзине:** есть заработанный подарок → янтарный блок `return_policy_gift`, иначе серый `return_policy_default`. Оба правятся в Настройках.

### Склады: выбор, разбивка заказа, лимит по остатку

- **Покупка ведётся от склада.** Товар, лежащий на двух складах, показывает **по одной цене, счётчику и кнопке на каждый склад** (и в списке, и в сетке). Товар с одним складом выглядит как раньше.
- **Строка корзины ключуется парой товар+склад (`cartKey`)** — один товар с двух складов = две строки со своими складами. Количество, удаление, галочки, массовое удаление работают по этому ключу. Снимок корзины для админки схлопывается обратно по товару (её таблица уникальна по user+product).
- **Заказ разбивается на документы 1С по складам** (`lib/order-warehouses.ts`): выбор клиента, иначе единственный склад с остатком, иначе склад с наибольшим; строки без остатка нигде — в хвостовой документ «без склада». При разбивке `site_order_id` получает суффикс (`ABC123-1`, `-2`, …), иначе 1С может слить документы; заказ с одним складом сохраняет голый номер. `Order.onecNumber` держит все номера, `onecSent` = true только если ушли все.
- **Склад передаётся и в шапке документа, и в каждой строке** — обработчик 1С заполняет колонку «Со склада» построчно.
- **Комментарий 1С про разбивку убран** — это внутренняя кухня, клиенту и 1С не нужна.
- **Нельзя заказать больше, чем есть на складе.** Решает **сервер**: `/api/orders` суммирует запрошенное по паре товар+склад и отклоняет **весь заказ** 409 с построчным списком («124-D — на складе «БК склад» 10 шт, в заказе 500»). Молча урезать нельзя: клиент рассчитывает на объём. В UI плюс упирается в остаток с подсказкой «На складе всего N шт», ручной ввод зажимается — и в каталоге, и в корзине (по остаткам из `/api/cart/reprice`). **Там, где остаток скрыт («>70»), лимит не ставится** — точного числа клиент не знает, решает сервер.
- **Остатки для клиента капятся: > 70 → «>70»** (`lib/stock.ts`), персонал видит точные.

### Цвета складов (`lib/warehouse-colors.ts`)

- Цвет закреплён за складом (`Warehouse.color`), правится в **Настройках**: 7 цветов, живой предпросмотр плашки, кнопка сброса на дефолт.
- Дефолты по имени (колонку не заполняли, поэтому новый склад из 1С сразу зелёный, как было): **БК склад — зелёный**, **БК склад 2 — синий**, **Car City склад — розово-красный** (намеренно НЕ фирменный `#E53935`: плашка в нём читается как кнопка), **Петя склад — графитовый**.
- **Нулевой остаток везде серый** — это состояние товара, а не идентичность склада.
- Цвет едет вместе с ячейкой остатка (`lib/stock.ts` → `lib/types.ts`), поэтому каталог, избранное, подарки и корзина согласованы.

### Оформление заказа

- Клиент выбирает **способ оплаты** (Наличный / Перевод) и **способ доставки** (Доставка / Самовывоз).
- **Адрес — из списка адресов клиента** (`ClientAddress`): один адрес рисуется текстом, несколько — радиокнопками с преднастроенным дефолтным. **Добавляет адреса только персонал** (ADMIN/RA — всем, MANAGER — своим, ACCOUNTANT — чтение): выбранный адрес не может приехать в 1С с опечаткой. Выбранный адрес **снимком** ложится в `Order.deliveryAddress` и именно он уходит в 1С, письмо и Telegram.
- **Комментарий для 1С** (`buildOneCComment`) — **БЕЗ префикса «Заказ с сайта №…»**: 1С подставляет его сама, дубль давал «Заказ с сайта №X. Заказ с сайта №X. Доставка…».
  - самовывоз → `Самовывоз`
  - доставка → `Доставка, Адрес: Казахстан, Алматы, Жибек жолы 11 (комментарий)`
- **Заказываются только отмеченные галочками строки корзины**; после оформления неотмеченные остаются. Выделение хранится как множество СНЯТЫХ галочек — товар, добавленный при открытой корзине, попадает в заказ по умолчанию.
- Заказ доступен **только роли CLIENT** и только активному аккаунту (`isActive`).
- Количество капится 100 000; WhatsApp-текст обрезается до 40 позиций.

### Правка заказа менеджером

- В «Заказах» разворачивается заказ → правятся количества строк (0 = не отгружаем), добавляется примечание клиенту, всё сохраняется одним действием. Итог пересчитывается, баланс следом.
- Право: **любая штатная роль, у которой есть раздел «Заказы»** (включая бухгалтера); клиент — 403; менеджер — только свои заказы.
- `OrderItem.qtyOriginal` пишется только при первой правке — повторные сравниваются с оригиналом.
- Клиенту: янтарная карточка и значок **«изменён»** (в «Моих заказах» и в админском списке), зачёркнутые старые количество и сумма, счётчик непрочитанных правок на пункте меню (`GET /api/orders/edited`), который гаснет после визита.

### Баланс и долг (`lib/balance.ts`)

- **Баланс = SUM(total − paid) по неотменённым заказам**, положительный = долг. Раньше долг начислялся разово при «Выдано» — свежий заказ не показывался, правка «оплачено» ничего не возвращала. Ручной редактор баланса убран: единственный рычаг — «оплачено» в «Заказах».
- **Долг считается только для статусов** `В работе` · `Выдано` · `Выполнен`; `Заказ принят`, `Отправлен`, `Нет в наличии`, `Отказ клиента` — не считаются (`DEBT_STATUSES`). Скрипт пересчёта дублирует список — он вне сборки и не может импортировать server-only модуль.
- Исправлен конфликт знака: карточка клиента считала долгом ПОЛОЖИТЕЛЬНЫЙ баланс, а плашка клиента и автоблокировка — ОТРИЦАТЕЛЬНЫЙ, из-за чего автоблокировка не срабатывала никогда. Теперь везде положительный = долг. **На проде это делает автоблокировку живой**: `debtSince` проставится ближайшим maintenance, первый блок возможен через `auto_block_days` (30) после деплоя; отключается «Автоблокировкой» = 0 в Настройках.

### Пароли

- `POST /api/auth/password` — своя смена (нужен текущий; сессии живут 30 дней).
- `POST /api/admin/clients/[id]/password` — сброс без текущего. Кто кого: **ADMIN** — всех; **RA** — всех, кроме ADMIN (иначе RA заберёт владельца и «Настройки»); **MANAGER** — только своих клиентов; **ACCOUNTANT** — никого. Хранится только bcrypt-хэш, пароли не логируются, общие правила — `lib/password.ts`.

### Уведомления о заказе

- **Почта** (`lib/mail.ts`): менеджеру клиента, запасной `ORDER_MAIL_TO`. Тема — **«Заказ с сайта №X — ФИО клиента»**. Тело по образцу заказчика: блок клиента + таблица `Наименование | Заказано | Срок | Направление | Кол-во | Сумма`; «Срок» — по остаткам, **«Направление» — склад, с которого строка реально заказана**.
- **Telegram** (`lib/telegram.ts`): нужен **полный токен с двоеточием** и `telegramId` менеджера. **Менеджер обязан сам нажать «Start»** — бот не пишет первым.
- Обе отправки best-effort и **логируют причину сбоя** (`[mail]`, `[telegram]`).

### Поиск

- Матч по sku/name/fullName + нормализованным полям + аналогам. Марка — фасет, **фильтр по модели = текстовый поиск слова в `full_name`**.
- **Exact match** — принудительно первым, ниже разделитель «Аналоги»; выделение рамкой + заливка `bg-accent/5`, **без иконок и бейджей «Аналог: …»**.
- **Автоочистка** строки при смене маршрута, КРОМЕ переходов с `?q=` (`components/SearchReset.tsx`).
- **История запросов** (localStorage, до 8) — выпадашка с иконкой часов.
- Поиск **переключает вид на список только на десктопе (≥ lg)**; на телефоне и в PWA остаётся сетка — список пришлось бы возить вбок. Ручной переключатель среди поиска не сбрасывается.

### Прочее

- **Заблокированный клиент** получает экран блокировки **вместо оболочки приложения** (layout — серверный компонент): ни сайдбара, ни контента ни на одном маршруте, только сообщение, контакты менеджера и «Выйти». Раньше это была модалка, и любая навигация её убирала.
- **«Акции» показывают только настоящие снижения**: `oldPrice > price`, и товар выпадает из списка, если наценка клиента подняла цену выше старой (наценки персональны, в SQL не выражаются — кандидаты фильтруются в памяти и пагинируются списком id).
- Менеджер **не может передать своего клиента** или снять закрепление (только ADMIN/RA). Новый клиент автоматически закрепляется за создателем.

## 4. Current State — реализованный UI/UX

### Каталог

- Вид по умолчанию — **сетка**; на десктопе поиск переключает на список (см. §3).
- **Покупка по складам:** в списке блоки складов складываются в три правые колонки (читается как мини-таблица внутри строки), в сетке — каждый склад в своём блоке с рамкой.
- **Локальный выбор количества:** цена (и зачёркнутая) пересчитывается на глазах, в корзину — по кнопке; зелёная вспышка «Добавлено», подсказка «В корзине: N шт». Плюс упирается в остаток склада.
- **Кнопка корзины — только иконка** на всех разрешениях (текст «В корзину» съедал полкарточки), пояснение в `title`/`aria-label`.
- **Обводки видимы:** рамки карточек и таблицы — `gray-300`, разделители строк — `gray-200`, при наведении карточка темнеет ещё на шаг. Раньше использовался самый бледный цвет палитры, и на белом сетка выглядела сплошным полотном.
- **Пустоты убраны:** колонка «Наличие» сужена 240 → 176px, освободившееся ушло применяемости (~160 → ~250px на 1440px), плашки складов `whitespace-nowrap`. В сетке применяемость **заполняет место, созданное самой высокой карточкой ряда**: слой `flex-1`, текст внутри позиционирован абсолютно, поэтому **высоту не создаёт** (обычный `flex-1` растягивал карточки до 929px), нижний порог `2.2rem`.
- **Подсказка с полным текстом применяемости** (`ClampedText`) — по наведению И по нажатию, только если текст обрезан, `position: fixed`.
- Пагинация сверху и снизу. Код 1С скрыт от CLIENT. Заглушка `/no-photo.png`. Дерево категорий на 3 уровня со счётчиками.
- Мобильный: сетка в 2 колонки, уменьшенные текст/отступы. (Фиксированная высота строк списка 92px снята — строки варьируются по числу складов, применяемость получает до 4 строк.)

### Корзина и заказ

- **Галочки на строках** + «Выбрать все / Снять выделение»; заказываются только отмеченные, итог/подарки/подтверждение считаются по выделению. **«Удалить выбранное (N)»** с подтверждением («Убрать из корзины отмеченные позиции: 2 из 4?»).
- Строки помечены складом; фото товара кликается и открывается лайтбоксом, артикул рядом ведёт в каталог.
- Выбор **адреса доставки** при «Доставке»; способ оплаты и доставки; подтверждение в `ConfirmDialog`.
- **Репрайс при открытии** (`/api/cart/reprice`) — «Итого» совпадает с тем, что спишет сервер; оттуда же приходят остатки по складам для лимита количества.

### Шапка и поиск

- **Кнопка поиска внутри поля** (акцентный красный квадрат 40px, инсет 4px) — как у Ozon/Amazon; отдельный магнифайер и декоративная иконка слева убраны, подсказка «/» видна только на пустом поле. Поиск при запуске **снимает фокус** с поля, чтобы на телефоне/PWA убралась клавиатура.
- **Крестик очистки** внутри поля (только когда есть что чистить), поле резервирует под него место; у инпута `transition` вместо `transition-all` — иначе текст прыгал при появлении крестика.
- **Кнопка WhatsApp из шапки убрана** (ссылка менеджера осталась в карточке контактов).
- **Мобильная шапка — две строки:** верхняя тёмная полоса во всю ширину (логотип-ссылка на главную по центру, бургер и телефон — белые кнопки 40px по краям; логотип белый-на-чёрном, `mix-blend-screen` растворяет его фон в полосе), нижняя строка на белом — поиск, уведомления, корзина со счётчиком. Выше `lg` — прежняя единственная строка, там логотип и корзина есть в сайдбаре. Все контролы 40px.
- **Мобильный вьюпорт зафиксирован 1:1** (`viewport` export, `user-scalable=no`) — в PWA с домашнего экрана пинч-зум ломал ощущение приложения; iOS чтит это в standalone-режиме.

### Кабинет клиента

- **«Мои заказы» — аккордеон**: только шапки заказов, состав раскрывается по клику; кнопка повтора не разворачивает карточку. Правленые заказы — янтарные, со значком «изменён», пояснением и зачёркнутыми старыми значениями.
- **«Возвраты» — вкладка внутри «Моих заказов»** (`?tab=returns`), `/returns` → redirect.
- Кнопка смены пароля (иконка ключа) рядом с именем в сайдбаре — во всех ролях, работает и в свёрнутом меню, и на телефоне.

### Админка
